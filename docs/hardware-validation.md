# 实机验证记录

日期：2026-10-22。环境：Ubuntu 22.04.5 LTS，AirPods Pro 3。
这份记录不包含设备蓝牙地址、用户配置文件或原始备份。

## 授权与连接

1. 耳机已配对并连接，BR/EDR ATT PSM `0x001f` 可连接。
2. 未配置 Apple DeviceID 时，读取通透句柄 `0x0018` 返回 `01 0a 18 00 0e`。
3. 用户运行仓库配置工具，设置 `DeviceID = bluetooth:004C:0000:0000`，重启蓝牙并重新连接耳机。
4. 再次读取成功，参数布局为 104 字节。

## 读取与写入

初始值：自定义通透关闭；左右耳增音、音调、环境噪声降低均为 0；对话增强关闭；
自己声音增音为 0.5。

执行修改：`enabled=true`，左右耳 `amplification=-0.2`。
工具在写入前保存完整原始值，收到 ATT Write Response 后读回，完整参数字节与请求一致。
随后关闭 ATT 连接，在另一次独立连接上重新读取，仍得到相同值。
实际浮点读数为 `-0.20000000298023224`，是 −0.2 的 float32 表示。

音调、环境噪声降低、对话增强和自己声音增音没有修改。

## BlueZ 接管 ATT 后的连接拒绝修复

随后 BlueZ 完成 GATT 服务发现，直接连接 PSM `0x001f` 返回 `ECONNREFUSED`，
而耳机仍处于音频连接状态。通过 BlueZ `ReadValue` 可以读取相同的 104 字节数据。

修复后自动按设备和 UUID 选择 BlueZ GATT 传输。实机 `doctor --json` 报告
`ok=true`、`backend=bluez`，返回当前参数。另进行了同值写入测试：先备份原值，
再经 BlueZ `WriteValue`（此特征只声明无响应写入）写回完全相同的值，随后
`ReadValue` 验证完整字节一致。没有改变任何调节参数，也没有重启蓝牙或断开音频。

## 尚未确认

- 用户主观听感与实际声音放大程度。
- 环境噪声降低、音调、对话增强和自己声音增音各项的听感效果。
- 蓝牙重连、切换到苹果设备、耳机重启之后的参数保持行为。
- 真实设备上的备份恢复流程（已通过模拟协议测试）。
- 其他 AirPods 型号和固件。

读回一致证明设备接受并保存了该参数值，不等同于证明它在所有聆听模式下都产生预期声音效果。

## 0.2 控制中心

2026-10-22：在同一副 Pro 3 上连接 AACP PSM `0x1001`，完成握手、功能协商和通知订阅。
收到左右耳电量、型号、固件、佩戴状态和通透模式通知。充电盒状态为 disconnected，
因此电量正确显示为未知，没有将其 0 值当作真实电量。

在用户级后台服务上执行通透 → 降噪 → 通透，每次切换都收到对应模式的设备确认。
保存当前声音设置及模式为本地预设，并成功重新应用。此预设中的声音参数与耳机原值一致，
因此没有额外写入声音参数；原先实机通透写入验证见上文。

尚未实机切换到自适应或关闭模式；这两项提供接口，但只在设备确认后才报告成功。
型号信息、实时电量和模式通过同一服务提供给 GUI 与 JSON CLI。


## 2026-11-13：高级参数通道与重连验证

再次复现音频已连接、BlueZ ReadValue 返回 ATT `0x0e`。Apple DeviceID 配置和适配器实际报告值均正确；通知订阅也返回同一错误。
旧服务每次操作后释放直接 ATT 通道，且 ConnectProfile 的 D-Bus 超时只有 8 秒；本次系统日志显示音频约 15 秒后恢复。

修复后，服务在重连时先建立直接 ATT 通道，再连接音频，并在操作之间保持通道。连接失败时释放通道；写入失败后不自动重发。重连延长等待时间，并在音频恢复后再次验证读取才报告设置就绪。

实机进行了两耳增音 −0.001 的临时写入、完整读回核对和从自动备份恢复；恢复后的完整参数与初始值逐字节一致。

持续读取和 AACP 状态轮询期间，捕捉到一次整条蓝牙链路断开（同时出现 HFP 断开日志）；随后恢复读取，参数保持一致。此断连的原因尚未确认，因此没有将本次验证视为长期稳定性通过。断开后，普通读取会报告离线，显式“重新连接”才会主动建立蓝牙连接。

75 秒 btmon 抓包中，修复后的直接 ATT 读取持续返回 104 字节；随后耳机以 HCI `Remote User Terminated Connection (0x13)` 主动断开，断开前音频仍在传输。此次断开前没有本机 HCI Disconnect 命令。停用应用控制通道后的纯音频对照连接曾连续保持 45 秒。进一步只打开直接 ATT、不启动 AACP 的测试，同样在约 30 秒后断开。因此保持 ATT 通道和延长超时并未解决整体稳定性问题。上游 Linux 文档也记载了伪装 Apple DeviceID 后短时断开的问题，并建议调参后恢复原身份。

### Limitation

原始 BlueZ `0x0e` 的固件侧触发原因仍未确认。上述修复解决通道释放和过早超时；长期稳定性仍需持续使用验证。


## 2026-11-13：会话初始化对照

从真实设备信息字段 10 读到 `8454688`，解码为 `8B34`，与该设备在 macOS 中的记录一致。
此前界面展示的 `81.2675000075000000.6589` 是字段 4 的组件版本。现优先显示市场固件版本，并在 JSON 中保留 `firmware_raw`。

以下均为读取测试，保持通透参数原值；故障均表现为耳机断开整条链路。

| 对照条件 | 结果 |
| --- | --- |
| 注册 AAP Client 主机 SDP 服务、监听 PSM `0x100b` | 未收到传入连接；仍在约 30 秒后断开 |
| 传统连接握手，各阶段间隔 250 ms，功能位改为上游 `D7` | 约 37 秒断开 |
| 临时停用 PulseAudio 原生 HFP/HSP，仅保留立体声音频 | 约 36 秒断开；通话配置已自动恢复 |
| 添加每 5 秒一次的时间同步 | 约 37 秒断开 |
| UARP 版本协商及型号、硬件、固件等信息查询 | 收到有效响应；仍断开 |
| UARP 查询成功后每 10 秒轮询固件信息 | 轮询收到响应，约 36 秒断开 |

这些结果不能证明某个完整的原生初始化方案无效，只排除了上述有限交互足以保持连接的假设。
`04 00 04 00 01 00 08` 按解析器和原生调用格式是能力查询；将其直接替代初始 Connect 帧的实验未完成有效连接握手，不能当作“新版连接协议验证通过”。

参考：[上游断连分析（9A348，固件与本次不同）](https://github.com/librepods-org/librepods/issues/782)、[AACP/UARP 协议解析器](https://github.com/pabloaul/apple-wireshark)。
实验代码和设备日志保存在本地研究目录，未作为已修复功能合入应用。


## 2026-11-17 音频优先的重连

设备为 AirPods Pro 3，固件 8B34。默认 Linux DeviceID 下，多次调用新版普通重连，连续观察 93 秒，BlueZ 立体声传输和 PulseAudio 的同一输出设备持续存在。

临时启用 Apple DeviceID 后，在同一副耳机上对照了以下顺序。

| 操作顺序 | 实机观察 |
| --- | --- |
| 重建音频，应用不打开高级或 AACP 通道 | 静音 PCM 连续播放 100 秒。随后 BlueZ 参数读取返回 ATT `0x0e`，直接 ATT 连接被拒绝。 |
| 先恢复音频，立即读取一次直接 ATT，随即关闭这个通道 | 初次返回 104 字节。持续播放 65 秒后，由 BlueZ 读回了完全相同的参数。 |
| 另一次音频重连后，在直接 ATT 上小幅调低两耳增音 | 写入后读回匹配，再写回原始备份并逐字节核对成功。同一轮稍后尝试 BlueZ 读取时报告未连接。 |

默认 Linux 身份下另做了一次相同顺序的对照。音频恢复后立即打开直接 ATT，读取返回 `0x0e`。随后三次 BlueZ 参数读取均报告未连接，三个检查点均有立体声音频传输。

### 修复后的实机验收

在同一副 Pro 3 上再次启用 Apple DeviceID。第一轮按旧代码等待系统发现通透特征，15 秒后应用报错。此时立体声仍已连接，关闭并重新打开的直接 ATT 通道可以读取 104 字节。该次连接的协议记录显示，音频建立约 46 秒后，耳机主动连接电脑的 PSM `0x001f`，随后 BlueZ 开始 GATT 服务发现。在同一连接上，BlueZ 成功发出写命令，连续十次读取均为目标值，恢复后的原始字节也一致。

同一环境中做了两次只读对照，均保持直接 ATT 通道打开。先连接音频再打开 ATT 时，连续播放 95 秒后仍能在原通道读回完整原值。先打开 ATT 再连音频时，播放 32 秒后整条链路断开；HCI 记录为耳机主动断开（`0x13`），断开前没有本机 Disconnect 命令。这组结果将可复现的主机侧触发条件定位到连接建立顺序。耳机固件内部的断开判定仍未知。

修订后的服务先建立音频。在 BlueZ 的特征可读时使用系统通道；发现尚未完成时，用单次操作内的直接 ATT 连接完成读写，随后释放。高级重连成功需要在初次读取并关闭通道后，重新取得通道并读到完整参数。普通读取、写入和恢复也会检查立体声传输。音频尚未就绪时，自动模式仅使用系统已经建立的 GATT 通道。

| 实机项目 | 通过条件及结果 |
| --- | --- |
| 三次独立运行，每次连续重连两轮 | 六轮均通过，包括最终版本的两轮。每轮新建立的同一立体声输出连续播放至少 90 秒。前 45 秒轮询原值，随后两耳增音各降低 0.001，后 45 秒轮询目标值，最终从备份恢复并核对完整字节。每次运行的第二轮均读到第一轮的原值。 |
| 桌面 GUI，120 秒不读取高级参数 | 在同一立体声输出持续播放。调整左耳滑条后，右耳同步，点击“备份并应用”后，BlueZ 从耳机读回与两侧目标完全一致的参数。恢复后再次加载，完整字节和两个滑条均复原。 |

这些结果覆盖本机的音频连续性和参数读写。实际听感取决于当前聆听模式和佩戴情况。长时间日常使用及其他固件仍需分别验证。

### 重复验证

在使用 PulseAudio 的实机上安装项目并激活虚拟环境后，可运行下列验收。该脚本调用与 GUI 相同的用户级服务。高级调节需已配置并可用。每轮会重新连接所选耳机，播放静音 PCM，在同一音频输出上持续读取 45 秒，小幅调低增音，再持续读取 45 秒，最后恢复并核对完整原值。脚本连续执行两轮并检查重连后的原值。若调节失败，输出包含已创建的备份路径。

```bash
python tests/hardware_tuning.py --mac AA:BB:CC:DD:EE:FF
```

## 2026-11-17 通透调节的听感问题

同一副 Pro 3（8B34）在多次改变通透参数后，佩戴者反馈听不出环境声变化。操作前的备份显示两耳增音曾从 +0.353 调到 −1.000。随后实机读取显示自定义通透已开启，控制通道报告通透模式和双耳佩戴。音频连接正常和参数读回一致都不足以验收此问题。

上游文档提到通透参数写入后发送 Headphone Accommodation 配置。上游 Android 应用的通透写入函数则只调用了 ATT 写入。本机在 AACP 连接中实际收到了 140 字节的辅助配置。应用会原样发送本次连接报告的兼容配置；在保持原有通透参数的测试中，套接字接受了发送，随后通透参数仍可读。发送成功本身不能证明固件将参数用于环境声处理。听感验收应在同一聆听模式和环境声下，比较两个增音值并恢复原设置。[上游协议](https://github.com/librepods-org/librepods/blob/89356c08cea3db0b6b54792d9329d09a87cc85fa/docs/AAP%20Definitions.md#customize-transparency-mode) · [上游写入实现](https://github.com/librepods-org/librepods/blob/89356c08cea3db0b6b54792d9329d09a87cc85fa/android/app/src/main/java/me/kavishdevar/librepods/data/Transparency.kt)

随后在通透模式下进行了双耳增音试听，两档随机排序，各持续十秒，每段都核对了参数、模式和辅助配置发送结果。第一轮受音乐干扰，未计入。在有效的一轮中，佩戴者在揭示参数前选出第一段风扇声更小，第一段为 −1.000，第二段为 0.000。试后恢复并复读了原参数。这个对照只覆盖增音，未比较有无同步消息，也未测量声压差。
